# Database Migrations Workflow (Alembic)

This guide outlines the standard workflow for generating and applying database schema migrations across the OneVote microservices.

Our architecture heavily relies on mapped volumes in `docker-compose.yml` for the development environment. This allows us to generate Alembic migration files entirely within ephemeral Docker containers and automatically sync them down to our local Windows/Host machine.

---

## 🏗️ Step 1: Modifying Your Models
When you need to make database changes (e.g., adding a table, adding a column), open the respective model file:
`backend/services/<service_name>/app/models/*.py` 

Make your standard SQLAlchemy structural modifications. 

---

## 🗄️ Step 2: Ensure the Database is Running
Alembic requires an active database connection to evaluate the current schema against your updated Python models. You must bring the PostgreSQL database online before generating revisions.

Run the following command from the project root:
```bash
docker-compose up postgres -d
```
*(Wait a few seconds for the database to fully accept connections).*

---

## ⚙️ Step 3: Generate the Migration Revision
You will now spin up an ephemeral container for the target microservice. Because the `entrypoint.sh` would normally attempt to spin up Uvicorn, we must explicitly override the entrypoint using `--entrypoint sh`.

Execute the following to generate the autogenerated migration file:

```bash
# Replace <service_name> with auth, identity, biometric, etc.
# Replace "your_commit_message" with a short description (e.g., "add_user_role")

docker-compose run --rm --entrypoint sh <service_name> -c "alembic revision --autogenerate -m 'your_commit_message'"
```

**Example:**
```bash
docker-compose run --rm --entrypoint sh auth -c "alembic revision --autogenerate -m 'add otp table'"
```

> [!NOTE] 
> Because of your `docker-compose.yml` volume mapping (`- ./backend/services/<service_name>:/app`), the newly generated `.py` file inside the container's `/app/alembic/versions` directory will instantly appear on your local VSCode file system!

---

## 🚀 Step 4: Applying the Migrations

### Local Environment
You do **not** need to manually run `alembic upgrade head` in development. 

The `entrypoint.sh` file implemented across all services evaluates the local `GLOBAL_ENV` string. In development mode, starting your services normally will automatically run the upgrade against postgres prior to Uvicorn spinning up.

```bash
docker-compose up --build
```

### Production Environment
In production (as outlined in `docker-compose-prod.md`), the CI/CD pipeline executes `alembic upgrade head` before spinning up the final, immutable containers. Normal containers are specifically told *never* to generate migrations.

---

## 🧹 Quick Troubleshooting: Dealing with Merge Conflicts
If multiple developers create migrations simultaneously for the same service, you may encounter branching conflicts. 

**To resolve Alembic Heads:**
1. Manually identify the divergent tail inside the `alembic/versions/` folder.
2. Edit the `.py` files to fix the `down_revision` pointers so they form a single chain.
3. Verify your chain inside the container:
```bash
docker-compose run --rm --entrypoint sh <service_name> -c "alembic heads"
```
